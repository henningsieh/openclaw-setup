# Provision a New OpenClaw Agent

Use when the owner asks for a new agent with its own workspace, its own channel, and its own model — not a rename of an existing agent (see `agent-identity-migration`) and not a repair of an existing agent's provider gap (see `model-route-change`).

Work phase by phase, report each phase with observed output, and let the owner decide the next phase.

1. **Preflight the instance before creating anything.** Run `openclaw --version`, `openclaw agents list --bindings`, `openclaw channels status --probe`. Read `openclaw.json` and record: `agents.ownership`, `agents.defaults.model`, `agents.defaults.modelPolicy.allow`, every existing `bindings[]` entry, and for the target channel provider its accounts, `groupPolicy`, `guilds.<id>.channels` map (present or absent), and `users` allowlist. Capture each existing agent's route table so you can prove afterwards that no route lost its owner. Back up the config first: `cp ~/.openclaw/openclaw.json ~/.openclaw/openclaw.json.bak.$(date +%Y%m%d-%H%M%S).<agentId>`.

2. **Create the agent with the CLI, never by hand-editing config.** Run `openclaw agents add <id> --workspace <dir> --model <provider/model> --non-interactive`. Omit `--bind`, because it binds the whole account and would capture every channel of the bot. Set the thinking level separately with `openclaw config set agents.entries.<id>.thinkingDefault '"high"' --strict-json`, because a `:high` suffix inside a model reference is not a valid form on this release. Confirm the model id exists in `openclaw models list` and is present in `agents.defaults.modelPolicy.allow`; when `agents.defaults.models` is an allowlist map, add the model additively rather than replacing the map.

3. **Seed the workspace from a real template.** `openclaw agents add` seeds `AGENTS.md`, `BOOTSTRAP.md`, `IDENTITY.md`, `SOUL.md`, `USER.md` and a git repo — keep their field names and format, then replace the content. Write `IDENTITY.md`, `SOUL.md`, `USER.md`, `AGENTS.md` and `TOOLS.md`; delete `BOOTSTRAP.md`; do not create `MEMORY.md`, because shared channel contexts never load it and durable facts belong in `AGENTS.md`/`TOOLS.md`/`USER.md` plus daily notes under `memory/`. Create `memory/`, then `git add` the files and commit. When the setup repo tracks workspaces directly, delete a nested `.git` left behind by `agents add` first, so the outer repo records files instead of a gitlink. Run `openclaw agents set-identity --agent <id> --from-identity` so the config identity matches the file. Verify the workspace sits on a persistent volume with `findmnt -T <dir>`.

4. **Copy the provider credential into the new agent's own store.** A new agent starts with an empty auth store; `agents.defaults.authInheritance` is an upgrade-only marker and does not hand the owner's provider profiles to a new agent. Prove the gap with `openclaw models auth list --agent <owner>` versus `openclaw models auth list --agent <new>`. Read the key from the owner agent's store — `cp ~/.openclaw/agents/<owner>/agent/openclaw-agent.sqlite /tmp/agent-store.sqlite` then query `auth_profile_store` where `store_key='primary'` for `profiles."<provider>:default"` — and paste it with `openclaw models auth paste-token --provider <provider> --profile-id <provider>:default --agent <new>`, with the key piped in on stdin. The resolver accepts both `api_key` and `token` credential types, so the paste command's type does not have to match the source profile's type. `openclaw models auth activate` does not transfer a profile across agents: it reports that the saved sign-in is no longer available. Keep the key out of transcripts, command lines and reports. Verify with `openclaw models auth list --agent <new>` and `openclaw models status --agent <new>`, where the provider must report `effective=profiles:~/.openclaw/agents/<new>/agent/openclaw-agent.sqlite`.

5. **Share the skills the work needs.** Skills in another agent's workspace `skills/` directory are invisible to a new agent; it sees bundled skills only. Add the directory once with `openclaw config set skills.load.extraDirs '["<abs path>"]' --strict-json`, then verify per agent with `openclaw skills list --agent <new>` — every intended skill must show `ready`. A skill folder inside the shared directory that is itself a symlink to elsewhere is skipped with `reason=symlink-escape`; that is expected for those entries and does not affect the real skills in the directory.

6. **Bind exactly one channel, copying the shape of a binding that already works in the same config.** Find the working reference first: read the bindings array and the reference channel's allowlist entry, and mirror both. A peer binding that adds `match.guildId` fails to match, because Discord channel inbound carries no guild id at match time and the extra field pushes the match onto the account-wide fallback. Write `match.channel`, `match.accountId`, and `match.peer.kind=channel` with `match.peer.id=<channelId>`, and omit `match.guildId`. Mirror the reference channel's `requireMention` and `users` values in the new allowlist entry, because the trigger behaviour lives there and not in the binding. Create the channel through the Discord REST API — token, headers and the allowlist rules are in [discord-channel-provisioning.md](references/discord-channel-provisioning.md). Apply the allowlist entry and the binding in one `openclaw config patch --file` call, because arrays replace wholesale, so the patch must carry the complete `bindings` array; run it with `--dry-run` first, then apply. Object fields merge without deleting, so remove a key with `openclaw config unset <dotted.path>` (for example a stale `requireMention`) and confirm the removal with `openclaw config get`.

7. **Verify in this order, and know which proof you cannot produce yourself.**
   - `openclaw agents list --bindings` shows exactly one binding for the new agent, and every pre-existing agent keeps all of its routes.
   - `openclaw doctor` is clean.
   - Routing: grep the gateway log for the new channel id and read `[routing] resolveAgentRoute: ... bindings=N` plus `[routing] match: matchedBy=binding.peer agentId=<id>`. The `bindings=N` count proves the runtime picked up the binding; when it still shows the pre-change count, the runtime holds the old snapshot.
   - A turn: from inside another agent's session use the `sessions_send` tool with `agentId=<id>`. The `openclaw agent` CLI and `openclaw gateway call sessions.send` are both refused with "would lose inter-session attribution" from an agent exec, so they cannot serve as the probe.
   - The Discord round trip needs a human sender by default: the adapter ignores messages authored by the bot's own account, and the channel `users` allowlist holds only the owner. To exercise a bot-authored turn, set `channels.discord.allowBots` to `"mentions"`, admit the bot account id in the channel's `users` list, and post a message carrying a real mention of the bot. Otherwise ask the owner to post in the channel, then prove delivery with `openclaw message read --channel discord --target channel:<channelId> --limit 5`: both the human message and the agent reply must be listed.
   - A turn in the agent's main session reports `delivery.status=skipped`, because a main session has no channel target; only a channel-routed turn proves Discord delivery.
   - When the owner asks whether an agent answers in a channel, answer with the sender histogram of that channel's session transcript, not with an inference from the config: read the session with `sessions_history` and count the distinct `senderId` values of its inbound user messages.

8. **Do not restart the Gateway from a chat session.** Config changes hot-reload where the reload plan allows it, but `bindings` sits in the `kind: "none"` group, so a binding change may need a restart only the owner can perform. Verify the runtime from config, CLI output and log lines; when a restart really is required, ask for it.

9. **Verify from observed output, not from bundled source.** Read config, CLI output and gateway log lines to judge behavior; reading minified `dist/*.mjs` is a time sink that does not change the outcome. Do not open an unrequested risk investigation — such as a channel-scoped tool gate — while the primary path is still unproven; surface it as a recommendation and let the owner decide.

## Working style for this task

- Present each phase with its observed output and the check that passed, then continue.
- When the next step needs a decision the owner must make, stop and ask that one question instead of choosing.
- Keep one source of truth: when a file is copied into the new workspace, remove the stray original (`gio trash <file>`) instead of leaving a duplicate.
- Commit the result as grouped commits (config, workspace files, handover doc) and leave unrelated working-tree changes uncommitted.
- Surface problems and errors rather than papering over them with workarounds.
- Inspect with the OpenClaw CLI and core tools (`config get`, `agents list --bindings`, `sessions_list`, `sessions_history`, `message read`); write a throwaway script only when no tool answers the question, and never to re-read a channel when `message read` or the session history already answers it.
- Answer the question that was asked, in as few words as it takes, before reporting the surrounding state. A question about one agent does not need a tour of the whole fleet.
- Advance one phase at a time and hand the next decision to the owner; when the owner says stop, stop probing and report the state instead of continuing the investigation. When the owner asks to work through the remaining steps together, do one step, report it, and wait instead of running ahead.
