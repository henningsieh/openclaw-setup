# Heartbeat Schedule Setup

Heartbeat is a system-owned automation job: cadence ticks come from the Automations scheduler (`openclaw cron list --all` shows `Heartbeat (<agent>)`), but all semantics — active-hours gating, delivery routing, prompt, NO_REPLY contract — live in `agents.*.heartbeat` config. Edit config, never the job row.

1. **Scope the block to one agent on multi-agent hosts.** `agents.defaults.heartbeat` applies to EVERY agent; with two agents both would deliver to the same channel. Pattern that verified-clean: set `agents.defaults.heartbeat` to `{"every":"0m"}` (disables recurring cadence for agents without a per-agent block) and put the full block under `agents.entries.<id>.heartbeat`. After the change, `openclaw cron list --all | grep -i heartbeat` must show exactly one `Heartbeat (<agent>)` row — a stale sibling row disappearing is the scoping proof.

2. **Use the right delivery fields.** `target` accepts only a channel id (e.g. `discord`), `owner`, `last`, or `none` — never combine channel+recipient there. The recipient (a Discord channel id like `1489...786`, a Telegram chat id) goes in `to`. The channel must already exist in the channel's allowlist config. Finish when `openclaw config get agents.entries.<id>.heartbeat` reads back `target` and `to` separately.

3. **Read the tick phase, and treat the window as a runtime budget, not a start time.** `every: "30m"` ticks fire on an epoch-anchored phase that is **not fixed**: it drifts when a long or skipped run shifts the next tick (observed across three consecutive days: :26/:56, then :22/:52, then :25/:55). Never quote a remembered phase — read it now from `cron list --all` (next-run column) and `cron get` (`schedule.anchorMs`, `state.nextRunAtMs`). `activeHours` then gates those ticks (`cron runs` shows `status: skipped, error: "heartbeat skipped: quiet-hours"`), so the run lands on the first tick inside the window — never on `start` itself. To shift the digest, move `start` just before the tick you want.

   **The gate is evaluated when the run finishes, not when it starts.** A tick admitted inside the window still ends `skipped: quiet-hours` if it completes after `end` — observed: a 06:55:06 run lasting 300,644 ms was discarded at 07:00:06 with a full duration and `deliveryStatus: not-requested`, and nothing reached the channel. So `end` must exceed the slowest expected run by a margin, and `timeoutSeconds` must be **less** than the window length, or a legitimate in-window run is killed by its own timeout. The first tick inside the window should sit early enough that even a slow run finishes before `end`. Tell the user the digest arrives on a tick, not at a chosen minute; exact-minute delivery needs a cron-expression automation job instead. Write the window, the timeout, and the prompt in **one** `openclaw config set --batch-file` call: chained per-path `config set` calls each re-read the file, so a concurrent writer aborts the whole chain with `The config file changed while this command was writing … so nothing was changed` (observed losing an entire window+timeout+prompt change). The mechanism and the alternative `--batch-json` form are in `model-route-change` step 3. Finish when the current tick time, the window, and the timeout are mutually consistent and the expected delivery time is stated to the user.

4. **The prompt is sent verbatim, so pin the output format.** Heartbeat runs have no chat context; a vague prompt yields rambling or empty-looking digests. Write an explicit numbered contract: exact steps (which commands to run), and the literal reply shape (line count, prefixes, language, "nothing else"). `isolatedSession: true` runs each heartbeat in a fresh session (cheap, no history) but makes a missing/weak prompt produce confused replies like "I don't see a current task". Set `model` per heartbeat for cost control.

   **The prompt, not the model, usually sets the runtime budget — so make the health check one command.** Five of six separate exec calls, or a bare `openclaw status` whose table render dominated the output, turned a 59-second turn into a 5-minute one and lost the window. Instruct a single combined shell line that prints one compact line (disk %, `MemAvailable`, gateway HTTP code, count of non-`ok` jobs) and forbid bare `openclaw status` and per-metric invocations. When a run overruns, do not reach for a faster model first: a heavier model and a higher thinking level are legitimate and are absorbed by a wider window, while prompt cost is paid on every run. Heartbeat config has no thinking field — `agents.entries.<id>.thinkingDefault` is the only lever, and it applies to every run of that agent, so name that side effect to the user.

5. **Never force-run the heartbeat job as a test.** `automations run <heartbeat-job> --force` during a live conversation gets deferred (`system heartbeat last` → `reason: requests-in-flight`) and, when it did execute in an isolated session, it ran WITHOUT the morning prompt — posting confused junk to the delivery channel and ending `error: heartbeat failed: agent-tool-failure`. The documented manual wake is also deferred while your own turn is live: `openclaw system event --mode now` returns `{"ok":true}` (queue acceptance only) and `system heartbeat last` then reports `reason: requests-in-flight` with a ~0 ms duration. A scheduled tick has no such dependency. So mid-conversation there is no prompt-in-hand test: **verify against the next scheduled tick**, or read the target channel directly. Re-run a test outside any live turn if an immediate answer is required.

   **A deferred wake is delayed, not dropped — attribute any delivery to its actual source.** Verified: a wake issued at 07:08 with repeated `requests-in-flight` deferrals executed ~12 minutes later and posted a digest at 07:20, with no matching tick receipt in `cron runs`. So a digest appearing right after your own manual wake is that deferred run, not proof the scheduled path works — match the message timestamp against `cron runs` before claiming a tick delivered, and never present a manual-wake delivery as scheduled-path verification.

6. **Verify with the right surfaces.** `openclaw cron get <jobId>` — job id from `cron list --all` — shows schedule, `state.lastRunStatus`, `consecutiveSkipped`; `openclaw cron runs <jobId>` lists per-tick finished entries with skip reasons; `openclaw system heartbeat last` shows the latest run's `status` (`sent`/`skipped`), `reason`, delivery `to`, and a content `preview`. A run is proven only when `status: ok` / `sent` appears **and the message is read back out of the target channel** (`message action:read` on the channel id, newest message) AND the user sees it; `skipped: quiet-hours` entries are correct gating, not failures.

   **Verify the message body, not just its presence.** A delivered digest can still violate the pinned shape: verified, one run posted only `Morgen, Human! Disk auf / bei 96 % – bitte Speicherwachstum zeitnah prüfen.` — greeting fused with a status clause, no `Status:` line, no `Vorschlag:` line — because the model compressed the contract. Treat present-but-malformed as a failed run, tighten the per-line prefixes in the prompt, and re-test.

   **Read run state after the run ends, and never report a delivery that was not read back.** A `cron list` column showing `running` describes the current tick, not the previous one: a run that had already finished 5 minutes earlier as `skipped: quiet-hours` was reported to the user as "still in progress, just wait", and the user accepted that false status. After a suspected run, re-read `cron get` `state.lastRunStatus`/`lastRunAtMs`/`lastDurationMs` — a tick whose `lastRunAtMs` is older than the report is finished, not live. A tick can also show `running` well past its own `timeoutSeconds` (observed 11 min against a 420 s limit) with no receipt yet — that is a pending receipt, not a delivered run, and there is nothing new to read while it sits there: wait for the receipt and read the channel instead of re-policing the column. Treat `{"ok":true}` from a CLI wake, and "the config was accepted", as evidence of nothing delivered; `openclaw system heartbeat last` and the channel read are the two surfaces that show the truth, and use both before telling the user it works.

Related facts: heartbeat config changes apply without gateway restart ("Change will apply without restarting the gateway"); rows appear/disappear on config reload. `every: "0m"` disables cadence only — event wakes still run.
