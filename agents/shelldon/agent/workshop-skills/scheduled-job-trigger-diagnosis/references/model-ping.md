# Scheduled model ping

1. Inspect existing jobs with `openclaw cron list --all --json`, model availability with `openclaw models list --all --json`, and authentication with `openclaw models status --json`; select the canonical provider/model and inspect auth status without exposing credentials, because a similarly named model on another provider does not use the intended quota.
2. Create a silent, isolated agent-turn job using the requested schedule and IANA timezone. For a daily 02:00 ping, the tested form is `openclaw cron add --name '<name>' --cron '0 2 * * *' --tz Europe/Berlin --exact --agent shelldon --session isolated --model '<provider/model>' --thinking low --fallbacks '' --light-context --tools '' --message 'Reply with exactly: pong' --no-deliver --timeout-seconds 120 --json`; set an explicit empty fallback list because a different provider cannot prove the intended quota was used.
3. Read back with `openclaw cron get <jobId> --json`; check enabled state, timezone, next run, model, thinking, empty fallbacks and delivery, because creation alone does not prove the intended settings.
4. When an immediate test is appropriate, run `openclaw cron run <jobId> --wait --wait-timeout 3m --json`; verify `status`, `provider`, `model`, response and usage in the completed receipt, and disclose that this test itself consumes quota. Report the actual input-token count even when the prompt is tiny, because agent bootstrap context can dominate usage.
5. Verify a requested specific runtime and account separately using its runtime evidence or provider usage display, because a successful model/provider receipt alone does not prove the Codex harness or a new five-hour window started. If that evidence is unavailable, state the limitation rather than claiming it worked.
