# Agent Email Account

One Mailcow mailbox the agent owns for sending on instruction and waking on incoming mail.

1. **Prove mail DNS with dig before creating the mailbox.** Reuse the four-class check in `host-stack-updates` step 4 (MX, SPF TXT, DMARC TXT, DKIM TXT) and finish only when all four answer, comparing a new subdomain against its parent pattern.

2. **Store the mailbox password as `env` kind when any agent script must authenticate.** `secret` kind is write-only and never reaches `exec` (gateway-only: IMAP plugin resolution, HTTPS egress); `env` kind reaches gateway-hosted `exec`. Reclassify the same entry instead of duplicating it:
   ```bash
   openclaw secrets store set NAME --kind env
   openclaw secrets reload
   ```
   Enter the value only in the no-echo prompt, never via `--value`. Check with `openclaw secrets store list` (kind shown, values masked) and `openclaw secrets audit --check` (`unresolved=0`).

3. **Prove sending with STARTTLS before announcing readiness, using a plain throwaway script.** Send via Python `smtplib` (`SMTP(host, 587)` + `starttls`), reading the password only from the environment and asserting presence without printing the value. Never scaffold a skill file for a one-off send; run the script via `exec` and delete it afterwards so no orphaned helper remains. Vary only the display name on one auth user (`Name <box@domain>`) so envelope-from and header address stay identical and SPF/DKIM/DMARC stay aligned. Finish when the script prints success and the message arrives with `DKIM-Signature d=<domain>`, matching `Return-Path`, delivered to inbox rather than quarantine.

4. **Wire inbound as gateway config: restricted reader first, reader auth proof second, IMAP account third.** Create the reader agent before enabling the plugin (isolated workspace, sandbox all/session/no-workspace-access, tools `minimal` allowing only `session_status`). Prove reader model auth before any live test mail: `openclaw models auth list --provider <p>` shows the main agent profile while `openclaw models auth order get --agent mail_reader --provider <p>` shows `none` for a fresh reader, so run `openclaw models status --agent mail_reader --check` and `openclaw agent --agent mail_reader --message "Reply exactly MAIL_READER_OK"` and finish this step only on `MAIL_READER_OK`. (`authInheritance` is defaults-only and a per-agent key is rejected by validation, so plan the reader's model route around credentials it can actually resolve.) Then configure the IMAP account with `allowedSenders`, `senderAuth min verified`, `deliver: false` for testing, then `openclaw config validate`. Prove the path with a test mail from an allowlisted sender: the log line `plugins imap: account=<id> ... strength=verified` confirms dispatch. A fresh reader with an empty auth store fails late as `missing-provider-auth` after dispatch, so never declare inbound working without the auth proof first.

5. **Answer every mail automatically with a polling automation, never with the IMAP plugin alone.** The plugin only dispatches to a reader; it never sends replies. Create one `every` automation (5 min) as the working agent that already holds model auth, `sessionTarget isolated`, `delivery mode none`, payload `agentTurn` ordering exactly one list-exec, per-mail reply composition in the sender's language, and one send-exec per mail. Keep the repeatable list/send logic in the helper script that sits beside `SKILL.md` inside the skill directory (step 6), never in an agent workspace. Track processed mail by UID watermark persisted in the job scratch (last UID plus UIDVALIDITY, re-baselined on UIDVALIDITY change), never by `\Seen` flags: any other client previewing the mailbox marks mail seen, and a `UID SEARCH UNSEEN` then skips it forever with no reply and no session — this failure was observed in production. The list step must use `UID SEARCH UID <last_uid+1>:*` (BODY.PEEK only, never a fetching mode that marks Seen) and advance the scratch watermark only after each mail's reply is accepted; `UNSEEN` as the new-mail test is forbidden. The send path enforces the allowlist, stamps a loop-protection header, and marks `\Seen` only after SMTP ok. Force-run once and finish only on `status ok`. Silence quiet polls or the owner gets a push every interval: gate the job with a trigger condition watcher that runs the list step headlessly and returns `fire: false` when no processable mail exists, because a quiet evaluation creates no run history and no notification; write the check read-only (BODY.PEEK only, 30 s budget, at most 5 tool calls) and fail it open (`fire: true` with a verify-mailbox message) so a broken check surfaces visibly instead of silently dropping mail. Keep `NO_REPLY` as the payload fallback for empty races and forced runs, since that token suppresses delivery. Disable the IMAP plugin account when polling takes over so each mail is processed exactly once.

6. **Share one mailbox across sending agents instead of provisioning one per agent.** Keep one auth user and vary only the From display-name per agent; validate the name in the shared send script against a fixed allowlist and reject anything else, with `--from-name` selecting the sender and `--uid` optional so owner-ordered fresh mail sends without a source UID. Keep usage, allowlist, and credential handling in one global skill at `~/.openclaw/skills/<skill-name>/SKILL.md` with its helper script in the same folder, referenced as `{baseDir}/<script>.py`; that root is the standard load path and needs no `skills.load.extraDirs` entry, so never put a shared skill under an agent workspace and never add the standard root to extraDirs. Append the skill name to each sending agent's explicit skills allowlist, merging instead of overwriting because explicit lists replace inherited ones; unrestricted agents load it automatically. Set restricted reader agents' skills to `[]` so they never load sender skills. Finish with `openclaw config validate` and `openclaw skills list --agent <id>` reporting `ready` / `openclaw-managed` for each sending agent, plus one read-only `list` run from the bundled script path.

Verification: four DNS classes answer; audit `unresolved=0`; test mail in inbox with valid DKIM; IMAP dispatch logged `verified` (plugin path) or scheduled test run `status ok` (polling path); threaded reply arrives in the recipient's inbox per mail. Prove SMTP delivery in the postfix container log (`docker logs mailcowdockerized-postfix-mailcow-1`), matching the send's queue id through `status=sent (... Saved)` — SMTP never APPENDs to the agent mailbox's Sent folder, so an empty Sent proves nothing and the recipient's inbox (plus spam) is the only valid check. Find an answering run's session with sessions_list (kind cron, label Automation: <job name>) and open it in the Control UI at chat/<agentId>/~key/ plus the session key minus the agent:<agentId>: prefix with colons replaced by slashes.
