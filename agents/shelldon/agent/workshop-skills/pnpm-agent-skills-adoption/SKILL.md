# pnpm Agent Skills Adoption

Use when a `pnpm-workspace.yaml` monorepo should consume AI agent skills shipped by dependencies (`skills/<name>/SKILL.md`), or when `pnpm approve` / `permissions` / `skills.dirs` behavior needs verification.

1. **Prove version and upgrade path first.** `pnpm --version` + `grep packageManager package.json` + `which pnpm`. Below 12.11.0 there is no `approve`/`permissions`/`skills.dirs` (`pnpm approve --help` fails with Command not found — expected, not broken). When corepack-shimmed (`/usr/bin/pnpm` → `corepack/dist/pnpm.js`), upgrade only via `corepack use pnpm@12.11.2`, then `pnpm install --frozen-lockfile`. Never `npm i -g pnpm`. No v12-minor codemod exists (`pnpx codemod run pnpm-v10-to-v11` is v10→v11 only). Finish when `pnpm approve --help` and `pnpm permissions list` both respond.

2. **Wire the link target before approving anything.** Default pnpm targets only existing `.claude/skills`, `.cursor/skills`, `.gemini/skills` (plus one agent-env dir). A repo keeping skills at `.agents/skills` must set it explicitly or an approved skill fails install with approved-but-no-directory:
  ```yaml
  skills:
    dirs:
      - .agents/skills
  ```
  Empty list disables the feature. Keep one canonical dir; do not add unused agent dirs. Expect pnpm to create `.agents/skills/.gitignore` containing `pnpm-*` on first link — track it. Finish when the YAML parses and the dir exists.

3. **Review content before approving, keep `allowBuilds` until ready.** `pnpm install` never fails on pending skills; `pnpm permissions list` shows `Awaiting approval`. Read each `skills/<name>/SKILL.md` in the store (`node_modules/.pnpm/<pkg>/node_modules/<pkg>/skills/`) for instructions the agent will follow every session — approving grants both build and skills surface. `pnpm approve <pkg> -y` records to `allowBuilds` while no `permissions:` key exists, to `permissions:` once it exists; do not add an empty `permissions:` prematurely or older peers stop seeing new build approvals. Finish when `permissions:` lists `{pkg}: {skills: true}` (or `build: true` where needed).

4. **Verify links, know the two non-obvious cases.** Each approved registry skill links as `pnpm-<pkg>-<skill>` (`/` → `+`, e.g. `pnpm-@tanstack+react-table-table-state`). Workspace `workspace:*` skills grant (`greendex-skills: build, skills`) but produce no link — only registry direct deps link. Docs examples can be placeholders: `drizzle-kit@0.31.11` ships zero `skills/` files (`npm pack --dry-run | grep skills` empty); `@tanstack/react-table@9.2.6` ships three real ones (`getting-started`, `table-state`, `migrate-v8-to-v9`). Prove a committed setup recreates links: fresh `git clone` of the branch, `pnpm install`, then `readlink .agents/skills/pnpm-<pkg>-<skill>` resolves into `node_modules/.pnpm` and its `SKILL.md` head reads correctly. Finish when `ls -la .agents/skills | grep pnpm-` shows the expected symlinks and `git status` shows only `pnpm-workspace.yaml`, `pnpm-lock.yaml`, and the inner `.gitignore`.

5. **For drizzle-kit 1.0 RC, gate on the ORM consumer — then patch the adapter with `pnpm patch`, don't stop.** Pin explicit identical build hashes for both (`drizzle-kit@1.0.0-rc.5-<hash>` as direct devDep, `drizzle-orm: 1.0.0-rc.5-<hash>` in catalog; `latest` stays stable, bare `rc` is stale). Kit has zero `peerDependencies`, so the ORM gate is runtime: RC kit asserts `compatibilityVersion === 14` plus resolvable `drizzle-orm/_relations` on every verb — kit without matching ORM fails everything. Then check every dependency that touches `db.query`: better-auth `drizzle-adapter@1.7.7` (latest) still issues old-style relational `where: <SQL>` / `orderBy: [SQL]` internally and dies on ORM 1.0 with `Unknown relational filter field: "decoder"` — its peer range allows the install, runtime breaks. Patch it with the supported workflow, not dist-hacking: `pnpm patch @better-auth/drizzle-adapter`, edit the copy, `pnpm patch-commit <dir>` (commits `patches/*.patch` + `patchedDependencies`, survives installs; `node_modules/.pnpm_patches` itself stays untracked). In the patch, convert the adapter's where-DSL to PLAIN filter objects (`{col: v}`, `{AND/OR/NOT: ...}`, `{in/notIn/like/ilike/gt/...: ...}` — the RC runtime maps these to correctly-aliased SQL) and relational `orderBy: [SQL]` to `{col: dir}` objects. Do NOT pass the prebuilt SQL through `RAW`: the relational query aliases the table, so verbatim SQL breaks (`where "user"."email"` vs alias `"d0"` — verified failure). Before editing, confirm the LIVE copy: the loaded adapter may be a pure re-export (`better-auth/dist/adapters/drizzle-adapter/index.mjs` is just `export * from "@better-auth/drizzle-adapter"`), so follow the `readlink` chain from the importing package's `node_modules` to the store dir and ignore stale peer-hash instances. Finish when the adapter-exercising suites are green (observed: 6/6 + 3/3 org tests) AND a fresh `git clone` + `pnpm install` applies the patch automatically (grep the installed copy for the patch marker) and recreates the skill links.

6. **Convert migrations with order preserved.** RC hard-fails on the old layout (`assertV3OutFolder` on `meta/_journal.json`): run `drizzle-kit up` from the database package for folder-per-migration (`<tag>/migration.sql` + `snapshot.json`), confirm SQL renames with zero content change. Then fix what `up` gets wrong: folder prefixes must be 14-digit `YYYYMMDDHHMMSS` (`formatToMillis` yields `NaN` → `invalid input syntax for type bigint: "NaN"` on fresh DBs otherwise), and a same-second batch sorts alphabetically, breaking FK dependency order (observed: empty-DB migrate dies on `organization.country`). Rename folders to ordered synthetic timestamps in the old journal order and prove it: migrate a disposable database from zero. Note `getMigrationsToRun` dedupes by folder NAME, so renames re-apply on existing DBs — plan a wipe→migrate→seed rehearsal where authorized. Finish when empty-DB `migrate` succeeds.

7. **Rewrite relations AND the client init — and keep the table-object split.** ORM 1.0 removes root `relations`/`one`/`many` callback helpers (`relations is not a function`, `many is not a function`). Centralize with `defineRelations(allTables, r => ({...}))` using `r.one.T({from: r.s.col, to: r.t.col})` / `r.many.T()`; old `fields/references` become `from/to`, old `relationName` becomes `alias`; add `optional: false` on every non-nullable-FK `one()` or output schemas go nullable (nullable FKs stay default). `defineRelations` returns NEW table objects (`relations.user !== user`): inserts/selects/updates/deletes keep working only on the ORIGINAL `pgTable` objects (`Cannot convert undefined or null to object` otherwise), while the `db` config and relational reads use the relations result — so keep schema exports original and wire only the client as `drizzle({client: pool, relations})`. Positional `drizzle(pool)` silently falls through to a localhost default (`ECONNREFUSED 127.0.0.1:5432`). Finish when `type-check` is clean.

8. **Relational `where`/`orderBy` accept only the new shapes.** `where: eq(...)` fails with `Unknown relational filter field: "decoder"` — use plain filters (`{email: x}`, multi-key = AND, `{AND/OR/NOT: ...}`, `RAW` only in callback form `((table, ops) => ...)` so column refs pick up the query alias — never verbatim prebuilt SQL (see step 5). `orderBy: [asc(col)]` is silently wrong (`order by "d0"."0" desc`) — use `{createdAt: "asc"}` objects; SQL expressions like `lower()` are impossible, so sort such fields client-side after fetching (verified: `localeCompare` with locale `de`, `sensitivity: "base"`, direction multiplier; safe when the query has no limit/offset, otherwise the DB order stands and the change must be recorded). Non-relational `.where(eq(...))` is unchanged. Then verify the battery: `db:generate` must run without crashing — a NEW migration folder means pre-existing schema drift, so inspect it and never commit drops blindly (no-diff is not guaranteed); plus `migrate` + no-op re-run, seed on a disposable DB, migration-chain, connection, shared-database, and every app suite touching `db.query`. Finish when all are green.

9. **Restore drizzle-zod mappings with a second patch — silent validation loss otherwise.** ORM 1.0 RC reports new `dataType` tags (`object date`, `object json`, `string numeric`, `number int32`, …) that drizzle-zod 0.8.3 does not match, so date/timestamp/integer/jsonb/numeric columns silently degrade to `z.any()` (verified: date-strings accepted, `distanceKm: "far"` accepted). Nothing throws — validation just stops rejecting. Diagnose with a leaf-type probe before assuming schemas are intact (`createInsertSchema(table).shape[col]`, unwrap `_def.innerType` to the leaf, `safeParse` a bad value; expect ZodDate/ZodNumberFormat/ZodUnion/ZodString per column kind). Survey every table via `getTableColumns` and compare `dataType :: columnType` pairs against the 0.x tags. Patch both published builds (`index.mjs` AND `index.cjs`): normalize the RC tags back at the top of `columnToSchema` (`object date→date`, `object json→json`, `string numeric→string`, `/^number int\d+$/→number`), leaving genuinely unknown tags untouched so new failures stay loud. Commit via `pnpm patch-commit` like step 5. Finish when the probe shows base-identical leaf types AND the rejection pins pass (observed: two openapi date-string pins went 403→400 because validation rejects again).

10. **Treat rotating full-suite failures as shared-state flake until proven otherwise.** When identical code fails in DIFFERENT files across runs (verified rotation: journey tests, then leg-procedure tests, then all-green on the same commit), the cause is the shared mutable dev DB (seed randomness, cross-suite residue, session state) — not the diff. Prove it before chasing code: re-run the failing file solo (expect green), then repeat the full run on a fresh wipe→migrate→seed (expect green). Reseed discipline: wipe (`DROP SCHEMA public CASCADE` + recreate, plus the `drizzle` journal schema where the project keeps it), `db:migrate`, second `db:migrate` as no-op check, `db:seed`, then the full run. A server-dependent suite (e.g. real-HTTP OpenAPI) needs its app server up first — a collection failure there is a missing server, not a code fault. If rotation SURVIVES fresh seeds, suspect worker-shared module state, not the DB: with vitest `isolate: false`, `vi.mock` variants and module singletons leak across files in one worker — verified symptom is auth-shaped flakes (`UNAUTHORIZED`/`FORBIDDEN` in files whose mocks pass solo) where several suites mock the same module differently (observed: seven files mocking `@/lib/better-auth` with different factories). Confirm by finding the config (`grep -rn isolate vitest.config.*`) and the competing mocks (`grep -rln 'vi.mock("<module>"' src`); fix with `isolate: true` (accept ~+15s jsdom startup per full run) and prove stability with two consecutive full-green runs — reseed discipline alone does not fix a mock leak. Finish when one full run is completely green on a fresh seed, or the remaining failure reproduces solo (then it is real — fix the code).
