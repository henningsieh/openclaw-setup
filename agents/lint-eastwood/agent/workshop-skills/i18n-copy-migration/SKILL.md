# UI copy migration

Convert hardcoded UI copy into locale-catalog keys in small, reviewable feature packages.

## Steps

1. Prepare the requested line. Run `git fetch --all --prune` and create the work branch from the release line the user names, not from a stale local main: `git switch -c <branch> origin/<release>`. If the working tree already holds the copy guard, stash only tracked manifest/config changes, keep the untracked guard script, switch, then reapply the manifest entries. Verify with `git branch --show-current` and `git status --short`.
2. Inventory before planning. Run the repo's copy guard; if none exists, build one with the `repo-policy-guard` skill. Record total warnings, file count, text-versus-attribute split, and top files. Run the same guard against the target release line when the checkout differs.
3. Read the i18n wiring. Confirm the message directory, supported locale list, request configuration, and the test that enforces identical key shapes. Note whether the app loads one bundle per locale or merges namespaces. If the user proposes one file per feature, recommend 6-9 domain bundles aligned to the package plan; per-feature files multiply loaders and type glue. If a single locale file is large, plan a mechanical domain-bundle split before translation and follow `references/domain-bundles.md`; rebuild the next-intl type at the same time.
4. Group warnings by feature ownership, not by file order. Produce 4-5 packages of roughly 60-140 warnings each; keep one cohesive feature per package and put the smallest package first to establish the pattern.
5. Write the package plan with scope, namespace, warning count, file count, order, acceptance criteria, and open decisions such as developer-only routes, brand names, and email placeholders. Derive scope from every guard warning whose path belongs to the domain, including all route groups; a preset directory list misses pages such as claim review routes.
6. For each package, add keys to every locale file in the same change. Keep the source locale canonical, translate the primary user locale, and leave other locales shape-complete; mirror source copy only until reviewed. Use semantic keys in a feature namespace, never English sentences as keys.
7. Replace JSX text and visible attribute literals with the translator. Use `useTranslations` in client components and `getTranslations` in server components; make the server component `async` and await the translator before rendering. Keep presentational loading skeletons as client components using `useTranslations`; async server components used as Suspense fallbacks render nothing under React Testing Library and break shared skeleton tests. Allow dynamic expressions and `t()` calls. Leave technical attributes, test IDs, class names, URLs, and API error catalogs untouched. Audit user-visible copy in object maps, conditional string expressions, and non-JSX modules such as `lib/themes.ts` separately; the JSX guard cannot see all of it.
8. Keep API error copy separate: error reasons and safe server messages belong to the API-error contract, not the UI copy pass.
9. Update tests to query roles, labels, or test IDs rather than rendered copy. When a component starts calling `useTranslations`, grep every test that renders it, including URL-state, integration, and child-component suites, and wrap each render tree in the repo's existing intl provider helper; a bare `render` throws missing context. If that helper does not accept render options, extend it to forward `RenderOptions` and `rerender` so the provider survives rerenders instead of bypassing it. Run the package's whole test directories, not only the component's own test file, and run shared cross-feature suites such as `src/components/loading-skeletons.unit.test.tsx` when shared skeletons change. Add a parity check only if the existing shape test does not already cover the new namespace.
10. Verify per package with `pnpm run type-check`, the focused test command, and `pnpm exec oxfmt --check <files>`. Run the repo linter on new TypeScript files before the commit hook; parent-relative imports and prefer-const failures otherwise surface only there. Confirm the scoped guard count drops to zero for touched files, the total count falls by the package warning count, and no new warnings appear elsewhere.
11. Land each package as its own commit only after its focused suite and type-check pass, then report the package, count drop, namespace, tests run, and remaining warnings. Before opening the pull request, confirm a spec or requirements issue covers the migration and link it; create the issue with the package scope and acceptance criteria when none exists, because a large refactor PR without a requirements record is hard to review. Do not start the next package on a red suite, and do not claim the whole migration is done until every package is closed.
12. For independent packages, delegate one at a time to a hidden subagent with `sessions_spawn`: `cwd` at the repo, `context="isolated"`, `completionTarget="parent"`, explicit paths/namespace/count, and instructions to report guard/tests/type-check and not commit. After it returns, run the full guard and shared cross-feature suites yourself, not only the subagent's scoped command; subagents can stop at their declared path scope and miss adjacent route warnings or shared regressions. Verify its diff and counts, then commit the package. Wire the same guard into pre-commit in staged mode with `pnpm run check:check-i18n -- --staged`; the script reads `git diff --cached --name-only -z --diff-filter=ACMR`, filters to the app scope, and exits 0 when no scoped files are staged. Test staged mode with one temporary hardcoded-copy file before relying on it.

## Rules

- Keep the guard warn-only in the normal lint chain while packages are being cleared; switch to `--strict` only when the total reaches zero. Do not add a baseline or ratchet unless the user asks; show every warning so progress is visible.
- Prefer a vertical feature slice over a cross-cutting all-labels pass; reviewers can verify one workflow at a time.
- Do not translate developer-only pages by default; exclude them from the guard or document the decision. When the user requires zero guard warnings, translate the page and keep the exclusion decision explicit.
- Do not mix API error semantics with UI copy migration; the error contract and the presentation catalog are separate tracks.
- Land the copy guard as its own commit before the bundle split and before the first copy package; keep the mechanical split in a second commit so reviewers can separate tooling, refactor, and copy changes.
